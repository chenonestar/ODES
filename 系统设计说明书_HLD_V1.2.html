01设计概述

1.1 设计目标

把需求书中六条彼此拉扯的约束同时满足，是本设计的全部难度所在：

约束对设计的实际压力
单文件、免安装、三平台排除 CGO，排除外部数据库与运行时，前端资源必须内嵌
全程离线排除任何 CDN、外部字体、外部 API；证书须在出发前取得并内嵌
匿名不可关联排除自增主键、排除时间戳、排除外键——这与常规数据建模习惯直接冲突
字段级加密排除 SQL 聚合——密文无法 GROUP BY，统计必须改为内存管线
作答端离线可填排除服务端翻页（htmx 风格），作答端必须自包含
自建测评网络进程内需承担 DHCP / DNS / 门户探测应答，且要能降级

1.2 设计原则

  1. 匿名性优先于一切便利。任何"顺手加个时间戳""用自增 ID 方便调试"的做法都要被拒绝，即使它让开发更舒服。
  2. 能在编译期或结构上杜绝的，不靠约定。例如作答记录表的实体结构中根本不定义时间字段，而不是"约定不写入"。
  3. 失败要响亮。现场没有第二次机会，启动自检、发布前置校验、擦除后残留校验都必须是硬失败，不能只打日志。
  4. 降级路径与主路径同等对待。内置 DHCP 失败、证书过期、主机故障，都必须有已设计、已测试的降级，而不是现场临场发挥。

2.1 明确排除的选项

排除项理由
SQLCipher / 整库加密需 CGO，破坏单文件与交叉编译（CON-07）。改为应用层字段加密
mattn/go-sqlite3同上，含 CGO

关于 ORM 的排除

这一条值得单独说明。多数 ORM 的默认行为——自增主键、自动时间戳、软删除标记——每一条都会在作答记录表上制造匿名性泄露。靠"记得关掉"来防守是不可靠的。使用 sqlc 从手写 SQL 生成代码，表结构由迁移脚本显式定义，使得"没有时间字段"成为一个结构事实而非纪律要求。

3.2 为什么管理端与作答端形态不同

05匿名隔离的物理落地

本章是整个设计的核心难点

需求书 NFR-ANO-020 指出了 V1.0 的关键缺陷：作答记录与令牌虽无外键，但插入顺序天然一一对应，两表各自 ORDER BY rowid 并排即可还原人码映射。本章给出该缺陷在数据层与代码层的具体封堵方式。

5.1 四项措施必须同时实施

#措施实现方式
1随机主键令牌表与作答记录表主键为 BLOB(16) 的 UUIDv4，由 crypto/rand 生成。建表时显式声明 WITHOUT ROWID，从物理上消除隐式自增序号
2不存时间两表的实体结构中根本不定义时间字段。迁移脚本经评审确认，CI 中加一条断言检查这两张表不含任何 *_at / time 列
3输出重排所有对外输出（统计页、评语列表、原始数据导出）必经 anon.Shuffle，匿名编号在输出时现场生成，不入库
4物理顺序打散见 5.2，这一项最容易被忽略，也最难做对

5.2 WITHOUT ROWID 是关键，但还不够

普通 SQLite 表以 rowid 为聚簇索引，插入顺序即物理顺序。改为 WITHOUT ROWID 后，表以主键为聚簇索引——由于主键是随机 UUID，物理存储顺序变为随机，与插入顺序无关。这一步用一个建表关键字解决了绝大部分问题。

但仍有两处残留：

  • WAL 日志保留了写入顺序。WAL 帧按事务提交先后排列，用工具解析 WAL 可以还原提交序列。
  • 页面分配在表增长时仍带有时间性痕迹。

处置：测评截止时（进入"已截止"状态的同时）执行一次 PRAGMA wal_checkpoint(TRUNCATE) 后跟 VACUUM。VACUUM 会按主键顺序重建整个数据库文件，随机主键使得重建后的物理布局与提交顺序彻底无关，同时 WAL 被截断。

这道防线的边界必须说清

在截止前，即测评进行过程中，WAL 里仍然有顺序信息。这符合需求书 NFR-ANO 承诺的边界——"非取证条件下不可关联"。管理员若在测评途中停掉程序、用取证工具解析 WAL，理论上仍可还原部分顺序。

这一点不应被掩盖，而应写入验收说明：NFR-ANO-091 的时序专项测试应在测评截止并完成 VACUUM 之后执行，这正是承诺成立的时点。

5.3 提交事务的取舍（ADR-004 的展开）

这里存在一个无法两全的矛盾，需求书 NFR-REL-011 与 NFR-ANO-020 在此正面相撞：

   方案 A：令牌置位与作答写入同一事务
   ┌─────────────────────────────────────────────┐
   │  BEGIN                                      │
   │    UPDATE token SET used=1 WHERE id=? AND used=0
   │    ── 影响行数为 0 则回滚（幂等保证）          │
   │    INSERT INTO answer (...)                 │
   │  COMMIT                                     │
   └─────────────────────────────────────────────┘
   ✓ 幂等严格成立，不会出现"令牌已用但作答丢失"
   ✗ 两次写入落在同一 WAL 帧，取证时关联性最强

   方案 B：两个独立事务
   ✓ WAL 中两条记录分离
   ✗ 中间崩溃会产生"令牌已用但无作答"或"有作答但令牌可重用"
   ✗ 参评人员提交后看到成功页，数据却丢了 —— 不可接受
图 5-1　提交事务的两个方案。

决策：采用方案 A。理由是失败代价不对称——方案 B 的失败会导致参评人员的票真实丢失，这是对测评有效性的直接破坏；而方案 A 的弱点只在取证条件下成立，已明确排除在承诺边界之外，且截止后的 VACUUM 会消除该痕迹。

补充措施：作答记录的 INSERT 在事务中先于令牌 UPDATE 执行，且事务提交前不返回成功页。这样即便解析 WAL，也需要额外推断两条记录的配对关系，而非直接读取。

5.4 anon 包的职责

函数用途
NewID() [16]byte密码学随机主键，全项目唯一入口，禁止其他地方自行生成 ID
NewToken() string≥128 位熵，Base32 去除易混字符（FR-TKN-020）
ShortCode() string8 位含校验位短码（FR-TKN-023）
Shuffle[T any]([]T)基于 crypto/rand 的 Fisher–Yates。所有对外输出前必调
Label(i int) string生成"作答记录 #N"，N 为重排后的位置，不入库

把这些集中在一个包里，是为了让 code review 有一个明确的检查点：凡是对外输出记录集合的代码路径，必须能追溯到一次 Shuffle 调用。

06字段加密与密钥生命周期

6.1 加密边界

状态字段
加密作答项答案、评语文本、测评对象姓名与职务、人员名单标识、测评说明文字
不加密项目名称、时间、状态、题目结构与选项、令牌值与使用标志、批次

令牌值不加密：它需要在每次请求时做等值查找，加密会破坏索引；且令牌本身不含身份信息，泄露它只意味着可以冒用一次作答机会，而非泄露身份。

6.2 密钥生命周期

   首次启动
     管理员设置口令 P
        ↓  Argon2id(P, salt, m=64MB, t=3, p=4)
     派生密钥 KEK ──────────────┐
                               │ AES-256-GCM 包裹
     随机生成主密钥 DEK ─────────┘
        ↓
     wrapped_DEK 存入 meta 表（可落盘，无口令不可解）
     salt 存入 meta 表

   每次启动
     管理员输入口令 P → 派生 KEK → 解开 wrapped_DEK → DEK 驻留内存
        ↓
     字段加解密使用 DEK，每字段独立随机 nonce

   进程退出
     DEK 随内存消失，不落盘、不写日志、不进快照
图 6-1　双层密钥结构。采用 KEK/DEK 分离而非口令直接加密数据，是为了让"修改口令"只需重新包裹 DEK，无需重新加密全部数据。

6.3 防护边界（必须诚实标注）

场景是否防护说明
笔记本失窃、数据文件被拷走有效这是字段加密的主要目标（RSK-05）
归档包在介质上被他人取得有效归档口令与登录口令不同，独立保管
防止管理员查看作答内容无效程序运行时 DEK 在内存中，管理员本就有权查看统计。字段加密不是用来防管理员的，防管理员靠的是第 5 章的匿名隔离
口令遗忘不可恢复无后门、无找回。设置时须明确告知（RSK-12）

把这三行写清楚，是为了避免后续评审中出现"既然加密了为什么管理员还能看到评语"这类误解——两套机制解决的是两个不同的问题。

07统计内存聚合管线

这是字段加密的直接后果，属架构级决策

作答答案以 AES-GCM 逐字段加密后，SQL 无法对其做 GROUP BY / COUNT / AVG。所有统计只能把行取出、在 Go 中解密、再内存聚合。若不在 HLD 阶段定死，sqlc 的写法会一路写到统计层然后推倒重来。

7.1 数量级验证

项估算
最大规模200 份 × 400 作答项 = 8 万个加密字段
AES-GCM 解密单次短文本约 1–2 μs（含 nonce 处理）
全量解密耗时约 80–160 ms
聚合计算纯整数计数，可忽略
合计< 300 ms，满足 NFR-PER-013（<1 秒）
峰值内存8 万条明文 + 计数器 ≈ 20–40 MB，满足 NFR-PER-022

结论：内存聚合完全可行，无需引入可搜索加密或部分明文冗余等复杂方案。尖刺③的任务是用真实数据量实测确认这组数字，而非探索方案。

7.3 口径规则的单点归属

需求书第 6 章的全部口径规则只允许实现在 internal/stats 一处：分母定义、弃权归并、比率舍入与调平、加权得分、小样本保护。PDF 导出、Excel 导出、统计页三个出口都调用同一份结果，不得各自计算。

理由：口径不一致是这类系统最典型的事故——报告里写 92.3%，Excel 里算出 91.8%，一旦出现就直接摧毁整套数据的可信度。恒等式断言（四档 + 弃权 = 100.0%）设为硬失败，宁可导出失败也不能输出自相矛盾的报表。

9.2 为什么不用 htmx

htmx 的模型是每次交互向服务端请求一个 HTML 片段。用在作答端会产生一个具体后果：参评人员翻到第 3 位测评对象时，如果此刻无线信号波动，页面就卡在那里。而这恰恰是会场里最可能发生的情形——两百人同时在场，人体对 5GHz 的吸收使后排信号明显劣化。

失败代价是不对称的：管理端卡一下可以刷新重来；参评人员卡住则可能直接放弃，而散会后无法补测。可靠性在这里压倒开发效率，详见 ADR-001。

9.3 体积控制

项预算
Alpine.js（内嵌）约 45 KB（gzip 后 ~16 KB）
作答端精简 CSS目标 < 20 KB。不复用管理端的 Tailwind 产物，单独构建一份只含作答端类名的 CSS
题目数据（JSON 内嵌）50 题 × 20 对象，含选项与说明，约 60–120 KB
单页合计目标 < 300 KB，优于 NFR-PER-014 的 500 KB 上限

启用 gzip 后实际传输约 60–90 KB。50 台终端同时加载约 4 MB，在 5GHz/40MHz 下耗时不足 1 秒——这印证了需求书的判断：瓶颈在射频关联而非带宽。

9.4 适老化要点

  • 字号三档，默认 ≥17px，切换状态存 LocalStorage，翻页后保持（FR-ANS-021）；
  • 等级选项整行可点，不要求点中圆点，触摸目标高度 ≥48px；
  • 已选项以填充色块呈现，不依赖细边框——老花眼下细线难以分辨；
  • 翻页按钮固定在底部安全区，不随内容滚动。

10.2 冷备接管流程

主机故障时（NFR-REL-021），冷备笔记本接管：

  1. 断开主机拔掉主机网线，避免两台机器同时占用 192.168.66.1 造成地址冲突。
  2. 拷入最近快照从 U 盘取最新的 snapshot/eval-N.db，覆盖冷备机的 data/eval.db。
  3. 设置网卡冷备机有线网卡设为静态 192.168.66.1/24，接入交换机。
  4. 启动并输入口令启动程序，输入管理员口令解开 DEK。这一步要求口令由考察组两人分别知悉——否则主操作人员不在场时无法接管。
  5. 验证用测试令牌走一次完整流程，确认服务恢复。
  6. 通告提示参评人员：已提交的无需重做；提交失败的重新扫码即可（令牌未被置位，仍然有效）。

目标：5 分钟内恢复，已提交数据最多损失 5 分钟。快照间隔与该指标直接对应。

一个设计细节

由于快照可能丢失最后几分钟的提交，这些令牌在恢复后仍为"未使用"状态，对应的参评人员会被要求重新作答——这正是期望行为。反过来的情形（令牌已用但作答丢失）才是不可接受的，第 5.3 节的同事务方案保证了这一点不会发生。

11架构决策记录（ADR）

编号决策取舍
ADR-001作答端采用自包含单页，不使用 htmx放弃开发效率与管理端的技术一致性，换取"页面加载后可离线填写"。依据是失败代价不对称：参评人员卡住无法补测。管理端仍用 htmx
ADR-002单进程、单二进制，内部分双前端形态符合"单文件拷贝即用"定位。管理端绑定回环即可获得隔离，无需拆进程。拆分会引入两个程序与一份数据库的协调问题
ADR-003统计走内存聚合，不用 SQL 聚合字段加密的必然结果。实测量级 <300ms，可接受。代价是 store 层不承担聚合职责，统计逻辑集中在 stats 包
ADR-004令牌置位与作答写入同一事务牺牲一点 WAL 层面的可关联性，换取严格幂等。理由是"票真实丢失"的代价远大于"取证条件下可关联"，而后者已排除在承诺边界外，且截止后 VACUUM 会消除
ADR-005作答记录与令牌表使用 WITHOUT ROWID + 随机 UUID 主键牺牲少量写入性能与存储空间（UUID 比自增整数占用大），换取物理存储顺序与插入顺序无关。这是匿名性的结构性保证，非纪律性约定
ADR-006不使用 ORM，采用 sqlc + 手写 SQLORM 默认生成自增主键与自动时间戳，每一条都会在作答表上制造泄露。手写迁移脚本使"没有时间字段"成为可被 CI 断言的事实
ADR-007自研 netsvc，不引入第三方 DHCP/DNS 库所需功能是极小子集（约 600 行），第三方库功能远超需要且带来依赖与体积。零依赖也便于安全审查——这是要向保密部门解释的组件
ADR-008必须使用自有域名 已修订原拟借助 nip.io 通配解析，该路径不成立：HTTP-01/TLS-ALPN-01 需公网可达（解析到私有 IP，够不着），DNS-01 需在 nip.io 下写 TXT 记录（第三方服务，无写入权限）。三种验证方式全部堵死。自有域名由此从"建议"变为硬性前提。详见 LLD 第 12 章与 ADR-010
ADR-009PDF 采用纯 Go 生成 + 内嵌思源宋体详见 LLD 第 13 章
ADR-010证书与域名配置化，程序不申请只装载否决"程序内置 ACME 客户端"的理由不是技术不可行——DNS-01 只需出站访问，办公室联网时笔记本完全能跑通。真正的理由是：DNS API 密钥的价值远高于证书本身（可为该域名下任意主机签发证书、劫持解析），而考察笔记本要被带出、置于会场、可能离开视线。可行性与应然性在此分离，特此写明以免后续以"技术上能做"为由重新引入。见 CON-08 与 LLD 第 13 章
